# 02 采购报价审查演示场景

> 文档状态：Deferred Synthetic Demo Specification
> 说明：仅允许虚构数据和受控 Fixture；不代表真实系统接入准入。

## Demo 目标

演示一个可审计的采购审查流程：平台把格式不一致的供应商报价转换成有证据支撑的比价结果，同时由授权人员保留最终决策权。

Demo 必须同时展示正常流程和 Fail Closed 流程，不能只演示一个看起来顺利的成功案例。

## 参与角色

| 角色 | Demo 中的职责 |
|---|---|
| 采购申请人 | 创建采购案例并上传材料 |
| 采购审核人 | 审查证据并作出最终决策 |
| 审计查看人 | 通过 `trace_id` 追踪完整决策过程 |
| 平台管理员 | 展示已发布配置和权限 |

P0 可以暂时把申请人和审核人映射到现有 `business_user` 与 `business_reviewer` 角色。生产上线前必须明确采购专用角色归属，并评审职责分离规则。

## 基准案例

某虚构企业计划采购 100 台商务笔记本电脑，交付地点为上海。

### 采购需求

| 字段 | 值 |
|---|---|
| Request ID | `PR-2026-0714-001` |
| Category | `IT.HARDWARE.LAPTOP` |
| Quantity | 100 |
| Target Currency | CNY |
| Budget | CNY 620,000 |
| Required Delivery Date | 2026-08-15 |
| Minimum Warranty | 36 个月 |
| Minimum Valid Quotes | 3 |

### 供应商报价

| 供应商 | 报价单价 | 运费和税费 | 交付 | 付款条件 | 质保 | 预设问题 |
|---|---:|---|---|---|---|---|
| Alpha Technology | CNY 5,900 | 已包含 | 20 天 | 验收后 30 天 | 36 个月 | 有效 TCO 最低 |
| Beta Systems | CNY 5,760 | 不含运费 | 35 天 | 预付 50% | 24 个月 | 单价低，但其他商务条件较弱 |
| Gamma Digital | USD 790 | 不含税 | 18 天 | 交付后 30 天 | 36 个月 | 需要经过批准的 FX 和税费标准化 |

所有名称和金额均为虚构数据。公开 Demo 数据集中不得使用真实供应商或员工信息。

## 准备材料

- 一份采购需求 JSON 或前端表单数据；
- 三份报价文件，至少覆盖 CSV、XLSX、文本型 PDF 中的两种格式；
- 一份已发布的采购制度 Snapshot；
- 一份已发布的 Scoring Profile Snapshot；
- 一份供应商主数据 Snapshot；
- 一份报价日期对应的已批准 FX Snapshot；
- 一套预期标准化结果和预期评分 Fixture。

## 正常流程演示步骤

1. 使用采购申请人账号登录。
2. 打开采购 Business App。
3. 创建 `procurement_quote_review` Workflow。
4. 填写采购需求并上传三份报价。
5. 启动 Workflow，并记录其 `trace_id`。
6. 展示文档提取结果及 Source Locator。
7. 展示供应商实体匹配候选及 Confidence。
8. 展示本次运行使用的 Policy 和 Scoring Profile 精确版本。
9. 展示标准化后的 TCO、商务条件和不可比较字段。
10. 展示 Weighted Score 之前执行的 Mandatory Policy Gate。
11. 展示 Scorecard、Risk Evidence、Assumption 和未解决问题。
12. 明确展示 Agent 推荐并不等于最终中标决策。
13. 使用采购审核人账号登录并打开 Approval Task。
14. 审查材料，填写意见并批准或驳回。
15. 批准后展示归档结果。
16. 使用 `trace_id` 筛选 Audit Log，检查 Workflow、Agent Run、Approval 和 Archive 事件。

## 正常流程预期结果

- 三份报价文件均关联到同一采购案例；
- 供应商匹配结果达到高 Confidence，或由人类显式确认；
- 所有金额根据已发布 FX Snapshot 转换为 CNY；
- 单价、运费、税费、质保、交付和付款条件分别展示；
- Scoring Formula 与基准 Fixture 的结果完全一致；
- Beta 不会因为报价单价最低就自动排名第一；
- 每个推荐结果都包含 Policy Version、Scoring Version 和 Evidence；
- Archive 前，Workflow 必须先进入 `waiting_review`；
- 只有人工批准才能使 Workflow 继续归档；
- 所有关键记录使用同一 `trace_id` 和 Tenant。

## Fail Closed 场景 A：缺少可比较数据

删除其中一份报价的运费金额和 Incoterm，并且不提供任何已批准默认规则。

预期行为：

- 系统把两个字段记录为未知；
- 不得把缺失运费当作 0；
- 该报价的 TCO 标记为不可比较；
- 根据已批准制度，推荐状态只能是 `insufficient_information` 或 `recommended_with_conditions`；
- 审查材料明确要求补充信息；
- 不得自动完成供应商决策。

## Fail Closed 场景 B：制度或配置不可用

禁用或移除已发布的 Procurement Policy 或 Scoring Profile。

预期行为：

- Graph 返回结构化、不可自动重试的配置错误；
- 不得使用备用虚构制度或由模型临时生成评分规则；
- Node 和 Agent Run 清楚显示失败原因；
- 只有授权人员修复并发布配置后才允许重试；
- 整个失败过程可审计。

## Fail Closed 场景 C：低置信度提取

提供一份受支持文件，其中税费或币种标识存在歧义。

预期行为：

- 提取字段包含 Confidence 和 Source Locator；
- 不得把低置信度值静默提升为已验证事实；
- 比价结果明确指出受影响的计算；
- 人工确认前不得批准受影响的推荐结果。

## LLM 和外部依赖行为

- 基准 Demo 必须配置已批准 LLM，除非所有被调用能力都提供确定性 Fixture Mode。
- LLM 不可用时必须返回可重试的技术错误，不能生成虚构输出。
- 供应商、制度、FX 或文件数据源不可用时，必须按照 IO Contract 返回来源明确的错误或 `insufficient_information`。
- 只有在 Version、Effective Date 和 Freshness Policy 允许时，才能使用缓存的 Policy 或 FX 数据。

## 必须展示的审计证据

Demo 至少要展示：

- Workflow 创建和启动；
- 每个文件的上传事件；
- Agent Graph 启动、完成或失败；
- 本次运行使用的配置版本；
- Approval Task 创建；
- 批准或驳回的人员及意见；
- Archive 操作；
- `trace_id`、Tenant、Business App、Workflow、Node、Graph、Run 和 User ID；
- Duration、Model Usage、结构化 Output Summary 和 Error Detail。

- [ ] 正常流程无需手工修改数据库即可完成。
- [ ] 至少演示一个 Fail Closed 场景。
