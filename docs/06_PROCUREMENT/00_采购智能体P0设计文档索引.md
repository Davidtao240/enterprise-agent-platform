## 评审结论

- 产品范围、Demo 场景、人机边界、评分基线、IO Contract、Graph 设计和 Tool 权限设计通过。
- Mandatory Technical Specification 已提升为 `blocker`，不能被价格或其他加权分数抵消。
- 标准案例要求三份有效报价；少于三份且无已批准例外时只能返回 `insufficient_information`。
- 允许开始 Phase A：平台安全前置补强、Finance Regression Fixture 和 Shared Capability 解耦。

## P0 产品决策

首个采购流程为：

```text
Purchase Requirement + Quote File
-> Evidence-Based Normalization and Comparison
-> Mandatory Human Procurement Review
-> Approved Result Archive
```

系统可以提出建议，但不得决定供应商中标、创建采购订单、联系供应商、修改主数据、批准发票或发起付款。

## 不可降低的准入条件

- 八份 P0 核心规范必须在写代码前评审批准。
- 每个 P0 案例都必须由人类作出最终决策。
- Policy、Score、Money Calculation 和 Required Field Check 必须确定性执行并版本化。
- Unknown Value 必须保持未知，不能静默变成 0。
- 每个重要结论必须包含 Evidence 或 Calculation Reference。
- Strict Domain Policy 和 Tool Permission 必须默认拒绝。
- 复用 Shared Agent 不能获得 Cross-Domain Tool 或 Data Access。
- Procurement 不得在 Platform Core 中引入业务条件分支。
- 连接采购数据前必须持续通过 Shared Core/Finance Regression，并完成 Durable Run 和 Tool Runtime 强制授权。
