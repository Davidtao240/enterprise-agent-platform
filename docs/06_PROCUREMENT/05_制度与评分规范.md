# 05 采购制度与评分规范

> 文档状态：Deferred Scenario Business Baseline
> 说明：确定性制度与评分规则继续有效，必须绑定 Published Version 和独立 Fixture。

## 目的

定义 P0 采购报价审查使用的确定性 Policy Gate、商务数据标准化、评分规则、置信度处理和推荐状态。

LLM 可以提取候选事实并解释已经校验的结果，但不得创造 Policy、Weight、Threshold、FX Rate、缺失的商务值或算术结果。

## 配置标识

每次运行都必须解析并保存以下已发布配置标识：

```json
{
  "policy_set_key": "procurement_quote_review_policy",
  "policy_set_version": "1.0.0",
  "scoring_profile_key": "procurement_general_goods_v1",
  "scoring_profile_version": "1.0.0",
  "effective_at": "2026-07-24T00:00:00Z"
}
```

Draft、Pending Approval、禁止新流程使用的 Deprecated、Disabled、Expired 或 Missing 配置，都不能用于新的 Workflow。

## 评估顺序

系统必须按照以下顺序处理：

1. 校验 Configuration；
2. 校验 Document 和 Entity 完整性；
3. 判断 Quote Comparability；
4. 执行 Mandatory Policy Gate；
5. 标准化商务数据并计算 TCO；
6. 执行 Weighted Scoring；
7. 生成 Risk Evidence 和 Confidence；
8. 生成建议性质的 Recommendation；
9. 强制进入 Human Review。

高 Weighted Score 不能覆盖 Blocking Gate。

## 数据质量状态

每个重要字段必须使用以下状态之一：

| 状态 | 含义 |
|---|---|
| `verified` | 直接来自 Source，并通过校验 |
| `derived` | 根据已验证 Input 确定性计算得到 |
| `declared_default` | 由已批准、已版本化规则提供，并明确标记 |
| `ambiguous` | 仍存在多个解释或实体匹配候选 |
| `missing` | 必需的 Source Value 缺失 |
| `conflicting` | 多个 Source 相互冲突，且无批准的优先规则 |
| `stale` | Source 超出允许的 Freshness Window |
| `not_applicable` | 已批准规则确认该字段不适用 |

只有 `verified`、`derived`、`declared_default` 和 `not_applicable` 可以进入最终可比较评分。`declared_default` 必须保留提供该值的 Rule Reference。

## 报价可比性

只有以下维度已经对齐或经过明确标准化，报价才可比较：

- 采购项目或规格；
- 数量和 Unit of Measure；
- 币种和 FX Effective Date；
- 税费是否包含及税率；
- 运费、保险、关税和其他 Landed Cost；
- 交付地点和适用的 Incoterm；
- 质保和服务范围；
- 交付日期或 Lead Time；
- Payment Terms；
- Quote Validity Period。

如果重要维度仍为 `ambiguous`、`missing`、`conflicting` 或 `stale`，该报价必须标记为 `non_comparable`。它可以继续显示在审查材料中，但不得得到具有误导性的精确排名。

## 强制制度门槛（Mandatory Policy Gate）

每个 Gate 返回 `pass`、`fail`、`warning`、`not_applicable` 或 `unknown`。

| Gate | 默认 Severity | 默认处理 |
|---|---|---|
| Published Policy 和 Scoring Profile 可用 | blocker | 技术失败，不进行评估 |
| 有效报价达到最少数量 | high | 无已批准例外时返回 `insufficient_information` |
| 必需采购规格完整 | blocker | 返回 `insufficient_information` |
| Supplier 满足全部 Mandatory Technical Specification | blocker | 不满足的 Supplier 必须标记为 `not_recommended` |
| Supplier Identity 已确认 | high | 歧义报价不进入最终排名 |
| Supplier Active 且 Eligible | blocker | 不得推荐受影响供应商 |
| Restricted 或 Suspended Supplier | blocker | 不得推荐受影响供应商 |
| Conflict of Interest Declaration 完整 | blocker | 问题解决前不得批准 |
| Currency 和 FX Source 有效 | high | 多币种报价标记为不可比较 |
| Tax 和 Landed Cost Basis 已知 | high | 受影响 TCO 标记为不可比较 |
| Budget Threshold | high | 标记超支并要求人工决策 |
| Required Delivery Date | 按品类为 medium 或 high | 按 Profile 扣分或阻断 |
| Minimum Warranty/Service Level | 按品类为 medium 或 high | 按 Profile 扣分或阻断 |
| Quote Validity 未过期 | high | 排除过期报价，除非存在批准例外 |

企业只能通过经过评审并发布的新 Policy Version 修改这些行为。

## 币种与成本标准化

### FX 规则

- 使用已批准 FX Snapshot，并记录 Source、Version、Base Currency、Quote Currency、Rate 和 Effective Timestamp。
- 禁止使用 LLM 估算汇率，也不能在无批准 Source Binding 的情况下直接使用公共实时汇率。
- 同时保留原币金额和标准化金额。
- P0 Monetary Value 统一保留 2 位小数，使用 Decimal `ROUND_HALF_UP`；不得使用 Binary Float 执行最终金额计算。
- 只在已发布 Formula 指定的 Component 或 Final Total 节点舍入，禁止在中间步骤重复舍入。

### P0 TCO 公式

对于供应商 `s`：

```text
goods_cost_s = normalized_unit_price_s * normalized_quantity_s

tco_s = goods_cost_s
      + freight_s
      + insurance_s
      + duty_s
      + non_recoverable_tax_s
      + required_service_cost_s
      + other_approved_cost_s
      - approved_discount_s
```

每个 Component 都必须是 `verified`、`derived` 或 `declared_default`。Unknown Component 不能当作 0；只要必需 Component 未知，`tco_s` 就必须是 `not_calculated`，对应报价标记为不可比较。

P0 不把主观风险、付款条件融资成本、交付延迟或质保差异直接换算为金额，除非已发布 Category Profile 定义了确定性公式和 Source Input。

## 默认评分方案

以下 Profile 已通过 P0 设计评审，作为首个 IT Hardware/Laptop Demo 的默认评分方案：

| Dimension | Weight | 确定性依据 |
|---|---:|---|
| Normalized Total Cost | 35 | 最低可比较 TCO 相对于供应商 TCO 的比例 |
| Commercial Terms | 20 | 已发布的付款、有效期、质保和服务子规则 |
| Delivery | 15 | 已发布的 Lead Time 或 Required Date 区间 |
| Technical/Specification Fit | 15 | 只评价达到 Mandatory Specification 之后的增值规格和适配度 |
| Supplier Performance and Risk | 10 | 只使用已批准 Supplier Master 指标 |
| Submission and Policy Completeness | 5 | 必需材料和 Gate Result |
| **总计** | **100** | Weight 必须精确合计为 100 |

Profile 可以按品类变化。Category Override 只有在已发布、所有 Dimension 都有定义且 Weight 合计为 100 时才有效。

Mandatory Technical Specification 先作为 `blocker` 执行。只有通过全部 Mandatory Specification 的 Supplier，才能进入 `Technical/Specification Fit` 加权评分；该评分只评价高于最低要求的性能、兼容性和服务差异。

## 分项评分（Dimension Scoring）

每个 Dimension 输出 0 到 100 的 Score 和对应 Rule Result。

### TCO 分数（Total Cost Score）

对于 TCO 为正数的可比较报价：

```text
cost_score_s = min(comparable_tco) / tco_s * 100
```

结果限制在 `[0, 100]`，并按照 Scoring Profile 舍入。不可比较报价返回 `not_scored`，不能返回 0。

### 区间规则维度（Rule Band Dimension）

Commercial、Delivery、Specification、Supplier 和 Completeness Score 根据已发布 Rule Band 计算。例如：

```json
{
  "rule_id": "delivery.required_date",
  "input": "2026-08-10",
  "required_by": "2026-08-15",
  "result": "pass",
  "points": 100,
  "evidence_refs": ["ev_gamma_delivery_01"]
}
```

LLM 可以把文本 Clause 映射成候选结构化值，但必须由确定性 Validator 应用 Band 和 Points。

## 加权总分（Weighted Score）

对于全部必需 Dimension 都已评分的供应商 `s`：

```text
weighted_score_s = sum(dimension_score_s,d * weight_d) / 100
```

如果必需 Dimension 为 `not_scored`，平台不得静默重新分配该项 Weight。除非已发布 Profile 明确定义 Missing Dimension Rule，否则 Overall Score 必须为 `not_scored`。

## 推荐区间

P0 已批准的默认方案：

| 条件 | Recommendation Status |
|---|---|
| Score 不低于 85，无 blocker/high Gate Failure，Evidence 完整 | `recommended` |
| Score 为 70 至 84.99，或存在可解决的重要条件 | `recommended_with_conditions` |
| Score 低于 70，或 Supplier 触发不可豁免 Blocker | `not_recommended` |
| 比价或必需 Evidence 不完整 | `insufficient_information` |

只有在报价可比较且无未解决 Blocker 时，Case Recommendation 才能指定 Leading Supplier。最终中标仍由人类决定。

少于三份有效报价时，如果没有 `approved_exception_ref`，Case Recommendation 必须为 `insufficient_information`。存在已批准例外后，系统才可以继续评分，并在 Review Packet 中突出展示例外的 Actor、Reason、Approval ID 和 Effective Scope。

## Tie 和 Sensitivity 规则

- Tie Tolerance 使用 Score Point 配置，P0 批准值为 `2.0`。
- 落入 Tolerance 的供应商按 Tie Band 展示，Agent 不得创造 Tie Breaker。
- 如果不确定 Input 的小幅变化可能改变排名，审查材料必须披露。
- 如果 Recommendation 不是最低 TCO 方案，必须列出导致差异的 Dimension。

## 置信度（Confidence）

Confidence 与 Supplier Quality 和 Score 相互独立。

| Confidence | 范围 | 处理规则 |
|---|---:|---|
| High | `0.90` 到 `1.00` | 确定性校验通过后可以作为提取事实展示 |
| Medium | `0.75` 到 `<0.90` | 显示 Warning 和 Evidence，提醒审核人关注 |
| Low | `0.00` 到 `<0.75` | 影响 Recommendation 时必须人工确认 |

Confidence 必须说明依据，例如 Extraction Quality、Entity Match Distance、Source Agreement 或 Evidence Completeness。模型自我声明的 Confidence 不能单独作为依据。

## 风险发现数据契约（Risk Finding Contract）

每个 Finding 使用以下结构：

```json
{
  "finding_id": "risk_001",
  "category": "commercial_terms",
  "severity": "high",
  "statement": "报价不含运费，且未提供运费金额。",
  "fact_or_inference": "fact",
  "confidence": 0.98,
  "policy_rule_id": "cost.freight_required",
  "affected_supplier_id": "supplier_beta",
  "evidence_refs": ["ev_beta_freight_01"],
  "recommended_action": "在完成最终比价前要求供应商补充运费报价。"
}
```

Severity 只能是 `blocker`、`high`、`medium` 或 `low`。没有 Evidence 的 Finding 必须标记为待确认 Hypothesis，不能支持不利决策。

## Policy 优先级

P0 设计评审批准以下默认优先级；生产 Tenant 可以通过新 Published Policy Version 调整：

1. 由已批准 Rule 表达的适用法律或强制监管要求；
2. Tenant Procurement Policy；
3. Category-Specific Published Policy；
4. Case-Specific Approved Exception；
5. Purchase Request Requirement；
6. Supplier Quote。

系统必须展示冲突，不能自行解决法律歧义。

## 配置变更治理

- Policy 和 Scoring 变更必须经过 Draft、Submit、Independent Approval、Publish 和 Deprecate Lifecycle。
- Author 不能批准自己的变更。
- Published Version 不可修改。
- Workflow 启动时绑定并保存精确 Version。
- 新 Version 不得改变正在运行或已归档案例。
- 每次变更记录 Author、Approver、Change Summary、Effective Date 和 Audit Trace。

当前平台 Configuration Governance 只支持 Business App、Workflow Template、Agent、Tool 和 Domain Policy。P0 实现前必须增加业务领域中立的 Policy Set 和 Scoring Profile 类型，或批准具备相同 Lifecycle、职责分离、不可变性和 Run Binding 的等价模型。禁止只把正式 Weight 写死在 Python 代码或 Prompt 中。

## 测试要求

P0 发布前，Fixture 必须覆盖：

- 同币种和多币种比价；
- 含税/不含税、含运费/不含运费；
- 数量和单位转换；
- 缺失值不得变成 0；
- 报价过期；
- 供应商实体无法确认；
- 供应商受限状态触发 Blocking Rule；
- Score Tie；
- Recommendation 与最低单价方案不同；
- Weight 合计不等于 100；
- Policy 或 FX 配置缺失/过期；
- TCO 和 Weighted Score 可以完全复算。
